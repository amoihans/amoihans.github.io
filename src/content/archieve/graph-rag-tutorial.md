# RAG痛点
- 无法多跳推理
- 缺乏全局性 不会全局归纳
- 切块带来的语义断裂 例如 苹果
一旦涉及关系、推理、全局归纳的问题 传统RAG就不行了
# GraphRAG
- 知识不是chunk 而是一张关系网图
- 基于图谱就行关联检索 覆盖更完整的上下文
- 知识图谱通过社区检测算法例如Leiden算法划分为若干社区，LLM为每个社区做摘要 全局问题就是用社区摘要来归纳
## 知识图谱构建步骤
- 文档切块
- 实体关系抽取
```MD
你是一个实体关系抽取助手。请从下面的文本中：
1. 识别所有的实体，每个实体给出：
   - entity_name：实体名（大写）
   - entity_type：类型（比如 [人物, 组织, 地点, 事件]）
   - entity_description：实体的综合描述

2. 识别所有实体之间的关系，每对关系给出：
   - source_entity：源实体
   - target_entity：目标实体
   - relationship_description：关系的描述
   - relationship_strength：关系强度（1-10 的数字）

文本内容：
{input_text}

请按以下格式输出：
("entity"|实体名|类型|描述)
("relationship"|源|目标|描述|强度)
例子
("entity"|刘备|人物|蜀汉的建立者，三国时期重要人物)
("entity"|关羽|人物|刘备的义弟，以忠义闻名)
("entity"|张飞|人物|刘备的义弟，勇猛善战)
("relationship"|刘备|关羽|桃园结义为兄弟，关系极为紧密|10)
("relationship"|刘备|张飞|桃园结义为兄弟，关系极为紧密|10)
("relationship"|关羽|张飞|桃园结义为兄弟|10)
```
- 对于重复和歧义 通过实体合并来消除
- 有了知识图谱 还需要社区检测 Leiden算法将图谱划分为不同层次的社区 从上到下从大变小
- 每个社区单独摘要 从上到下就有不同层次的摘要 
- 构建的过程很费token
## 查询步骤
本地搜索
- 问的是针对某个实体的问题
- 用问题向量去检索所有实体节点 找最相关的实体
- 从实体出发 顺藤摸瓜找邻居 关系 原始文本 社区报告摘要
- 组装以上信息给LLM
全局搜索
- 问的是全局 宏观的问题
- 先把全局问题拆分成多个社区内部的子问题 再汇总
 - 把某个层级的社区报告都拿出来分批生成中间答案 map遍历
 - 观点汇总 按评分排序 保留最重要的 LLM合并 reduce合并保留
- 全局很消耗token 因为需要遍历 

## 难点
- 索引成本高
- 实体歧义消除 LLM不知道一些依赖上下文的黑话
- 查询延迟 尤其全局 因为需要遍历
- 增量更新难 几乎全量 只能定期重建
 - 可能引入歧义项 需要消除
 - 图结构变化 导致社区需要重新划分
 - 向量索引变化

 # LightRAG
 核心是去社区化 社区带来了增量更新难的问题

创新在
- 图增强的文本索引 不做社区 也不做社区摘要 只把实体和关系的描述向量化
- ♥ 双层检索范式 全局性问题 把查询本身拆成两层关键词 分别检索 低层直接检索实体层（点） 高层检索关系层（边） 对二者结果进行融合
- 增量更新 没有了社区 所以直接追加
